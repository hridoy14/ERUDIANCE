# Monthly strategy, weekly seven-item batch, Social OS final verification (v2.2)

## Trigger and scope
One action `@Erudience linkedin image` accepts a topic, campaign, or a request to plan the month. Generate a 30-calendar-day plan, with 30 daily slots only when the owner chooses daily posting. Otherwise plan a sustainable cadence and mark non-posting dates. Do not assume that daily posting guarantees growth. Use business timezone Asia/Dhaka unless account settings establish otherwise. Separate calendar dates from publication timestamps; verify account timezone and scheduling constraints.

## Monthly strategy gate M0
Verify current business objectives, ICP, offers, landing page, available proof, audience geography, LinkedIn policies, brand assets, Social OS capabilities and prior performance. Do not invent analytics. Define measurable hypotheses: qualified leads, website clicks, consultation requests, saves, relevant comments, and impressions as diagnostic only. Document evidence URLs, dates and confidence. Produce 30-day calendar: content_id, local_date, week, pillar, buyer stage, buyer pain, claim/evidence, hook, post copy, visual thesis, format, CTA, landing page UTM, metric target as hypothesis, status, dependencies. Balance awareness/consideration/conversion based on business needs, not arbitrary universal percentages. Controller must approve monthly plan before batch production.

## Weekly refresh W0
At the start of each seven-day batch, recheck LinkedIn policy, source freshness, buyer relevance, offers, performance signals if connected, trend authenticity and schedule conflicts. Freeze a snapshot and record changes from monthly baseline. Do not blindly follow trends; check relevance, evidence and brand fit. A plan change invalidates dependent briefs and prompts.

## Weekly batch production W1-W7
In ONE production session, for the next seven scheduled calendar days (or seven content slots when specified), create a unique content record, original researched copy, creative brief inferred from content, brief controller PASS, prompt engineer revision, prompt controller PASS, genuine brand assets, rendered image, mechanical and visual QA, independent final controller PASS for each item. For each content item, use unique immutable ID and hashes. An item failing a mandatory gate remains BLOCKED; never substitute placeholder images or unverifiable claims. Do not count a blocked item as ready. Batch manifests include expected_count, ready_count, blocked_count, missing evidence and content hashes. Reject batch as fully ready unless all intended seven items pass.

## Approval and Social OS integration W8-W11
Distinct states: PLANNED -> BRIEF_APPROVED -> IMAGE_VERIFIED -> OWNER_APPROVED -> UPLOAD_AUTHORIZED -> UPLOAD_REQUESTED -> REMOTE_VERIFIED -> SCHEDULED_VERIFIED (only if schedule was explicitly authorized). Owner approval of the creative does not grant Social OS write access. Explicit write authorization must name social.erudience.com, exact seven content IDs, target workspace/channel, whether drafts only or scheduling, and proposed dates/times. Never publish automatically. A general wish for future weekly uploads does not authorize an immediate write.

Before any write, discover an authenticated, supported Social OS connector or documented API, confirm schema, allowed media formats, upload endpoint, workspace, draft/schedule behavior, idempotency and rate limits. Never invent endpoints or authentication. If only browser is available, require user authorization and inspect UI, then verify remote state. If unavailable, output upload-ready package and BLOCK remote completion.

For each authorized record, send exact text, image, metadata, schedule only if separately approved, and idempotency key. Verify response with remote read-back: record ID, workspace, image attachment checksum where available, caption exact match, destination, scheduled time/timezone, status. API success response alone is not remote verification. Retry safely with idempotency and backoff; no duplicate posts. If remote record differs, mark REJECT, repair only with fresh authorization if a remote change is needed, and re-read. Final authority is verified Social OS remote record, not a local receipt. Produce batch reconciliation report and evidence receipts; do not claim complete if fewer than intended items are remote-verified.

## Measurement feedback
Only after actual publication, collect available LinkedIn analytics through permitted integration, with timestamps and provenance. Separate organic reach, relevant engagement, qualified leads and attributed conversions; use UTMs where supported. Weekly report: produced/approved/uploaded/scheduled/published counts, exceptions, top hypotheses, leading indicators, and changes for next batch. Never infer lead counts from impressions. No persistent autonomous weekly execution without a real scheduler/automation integration.

## Controller contract and denial rules
Every stage output: `content_id`, `stage`, `input_sha256`, `output_sha256`, `source_refs`, `timestamp_utc`, `verifier`, `decision`, `failure_codes`, `next_stage`. PASS only with required evidence; FAIL routes to owning stage; NOT_VERIFIED blocks. Invalidation cascades after any upstream edit. Bounded 3 repair attempts per content item per stage; then ESCALATE. Remote verification must check the actual remote object. Do not claim 100% correctness or guaranteed growth.
